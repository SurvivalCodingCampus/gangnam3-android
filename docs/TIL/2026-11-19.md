# 1. 배운 점

- **디자인 속성은 프로젝트 전용으로 만들어 쓰기**: 기본 제공 값/컴포넌트를 화면마다 그대로 가져다 쓰면 디자인이 바뀔 때 고칠 곳이 흩어짐. 프로젝트 전용 색상, 타이포, 컴포넌트로 한 번 감싸 두고 그걸 참조하는 게 수정하기 쉬움.
- **Stability 확인 플러그인**: IDE 플러그인을 설치하면 컴포저블 파라미터가 Stable인지 Unstable인지 코드 옆에 표시해 줌.
- **`@Composable` 람다를 파라미터로 받기**: `content: @Composable () -> Unit`처럼 UI 자체를 파라미터로 넘길 수 있음

## drawable과 화면 밀도(dpi)

> 기기마다 화면 밀도(dpi)가 정해져 있고, Android는 기기 밀도에 맞는 `drawable-xxx` 폴더에서 이미지를 찾음. 맞는 폴더에 없으면 다른 밀도의 이미지를 **자동으로 확대/축소**해서 씀.

| **폴더** | **mdpi** | **hdpi** | **xhdpi** | **xxhdpi** | **xxxhdpi** |
| ------ | -------- | -------- | --------- | ---------- | ----------- |
| **밀도** | 160dpi   | 240dpi   | 320dpi    | 480dpi     | 640dpi      |
| **배율** | 1x (기준)  | 1.5x     | 2x        | 3x         | 4x          |

- **정석**: 밀도별로 크기를 맞춘 이미지를 각 폴더에 넣어 둠.
- **자동 확대의 문제**: 저밀도 이미지만 있으면 고밀도 기기에서 확대돼 **흐릿**해지고, 확대된 크기로 디코딩되니 **메모리 사용량이 크게 늘어남**. 한정자 없는 `drawable/`도 mdpi로 취급되므로, 여기에 고해상도 이미지를 넣으면 xxhdpi 기기에서 3배로 확대돼 OOM의 원인이 되기도 함. (늘어나는 건 APK 용량이 아니라 런타임 메모리)
- **`drawable-nodpi`**: 밀도와 상관없이 **크기 조절을 하지 않는** 폴더. 원본 픽셀 그대로라 기기마다 보이는 크기가 달라지니 주의.
- **아이콘은 Vector Drawable(xml)**: 벡터라 밀도별 이미지를 따로 만들 필요 없음.

## 문자열 리소스

- `res/values/strings.xml`에 정의하고 `stringResource(R.string.xxx)`로 사용. 하드코딩 대신 한 곳에서 관리 가능.
- **다국어**: `values-ko/strings.xml`, `values-ja/strings.xml`처럼 언어 한정자를 붙인 폴더를 만들면 기기 언어에 맞게 자동 선택됨. 기본 `values/`는 대체용(fallback)이라 반드시 있어야 함.
- **포맷 인자**: `<string name="hello">%1$s님 안녕하세요</string>` → `stringResource(R.string.hello, name)`

## MVVM

> **Model - View - ViewModel**로 역할을 나누는 아키텍처 패턴. View는 ViewModel의 상태를 **관찰해서 그리기만** 하고, ViewModel은 View를 **모름**.

| **구분**        | **역할**                                      | **예시**                 |
| ------------- | ------------------------------------------- | ---------------------- |
| **Model**     | 데이터, 데이터 비즈니스 로직                            | Repository, DataSource |
| **ViewModel** | 화면 로직, 화면에 표시할 데이터와 상태(로딩, 에러 등) 보유, 이벤트 처리 | `RecipeViewModel`      |
| **View**      | UI 그리기, 사용자 이벤트를 ViewModel로 전달              | Activity, Composable   |

### 상태 관리

> 앱에서 변하는 데이터(상태)를 **어디에 두고, 누가 바꾸고, 바뀌었을 때 화면에 어떻게 반영할지** 정하고 다루는 것.

- **상태(State)**: 시간에 따라 바뀔 수 있는 값. 예: 입력한 검색어, 불러온 목록, 로딩 중 여부, 체크박스 선택 여부.
- 상태가 여기저기 흩어져 있으면 같은 값이 서로 달라지거나 화면 갱신을 빠뜨리는 문제가 생김 → 상태를 한 곳에서 관리하고, 바뀌면 화면이 자동으로 따라오게 만드는 게 핵심.

### ViewModel 특징

- **화면 하나에 ViewModel 하나**가 일반적. 여러 화면에서 재사용하면 상태가 섞이고 책임이 커져서 문제가 많음.
- **구성 변경(화면 회전 등)에도 살아남음**. 단, `rememberSaveable`과 달리 **프로세스 종료**(시스템이 메모리 회수) 때는 사라짐. 이것까지 버티려면 `SavedStateHandle` 사용.
- **`onCleared()`**: ViewModel이 완전히 소멸될 때(화면 종료) 호출. 리소스 정리용.
- **`viewModelScope.launch`**: `onCleared()` 시점에 자동으로 cancel됨. 화면을 나가면 진행 중인 코루틴이 알아서 정리됨. 기본 디스패처는 `Dispatchers.Main.immediate`.
- **테스트는 ViewModel 위주로**: 화면 로직과 상태가 모여 있고 Android UI 의존이 적어서 단위 테스트하기 좋음.

### ViewModel의 상태: Compose State vs StateFlow

- ViewModel 안에서 `mutableStateOf`로 상태를 가져도 동작은 함.
- 그래도 **StateFlow**를 많이 쓰는 이유:
  - Compose 런타임에 의존하지 않아 View(XML) 시스템이나 다른 모듈에서도 사용 가능
  - `map`, `combine` 등 Flow 연산자로 상태 조합 가능
  - 단위 테스트에서 값 검증이 쉬움

### collectAsState vs collectAsStateWithLifecycle

| **구분**       | **`collectAsState()`**           | **`collectAsStateWithLifecycle()`**          |
| ------------ | -------------------------------- | -------------------------------------------- |
| **소속**       | Compose 런타임 (플랫폼 무관, 멀티플랫폼 가능)   | `lifecycle-runtime-compose` (**Android 전용**) |
| **수집 중단 시점** | 컴포지션에서 빠질 때만. 앱이 백그라운드로 가도 계속 수집 | Lifecycle이 `STARTED` 아래로 내려가면 중단, 돌아오면 재개    |
| **결론**       | 백그라운드에서 불필요한 작업이 돌 수 있음          | **Android 앱에서는 이걸 권장**                       |

## Activity 생명주기 & Application

- **`onPause()`**: 화면이 일부 가려지거나 포커스를 잃었을 때 (반투명 Activity, 멀티 윈도우 등).
- **`onStop()`**: 화면이 완전히 안 보일 때 (홈 버튼, 다른 Activity가 전체 화면으로 덮음).
- **`finish()`**: Activity를 직접 종료 → `onPause` → `onStop` → `onDestroy`. 뒤로가기를 누른 것과 같은 결과.
- **Application**: 앱 프로세스당 **하나만** 생성되고 프로세스가 끝날 때까지 살아 있음 → 사실상 싱글톤. Repository처럼 앱 전역에서 공유할 객체를 두는 곳으로 씀.
  - **`by lazy`**: 처음 사용할 때 생성하는 지연 초기화. 앱 시작 시 한꺼번에 만들지 않아서 시작 속도에 유리.

```kotlin
class RecipeApp : Application() {
    val recipeRepository by lazy { RecipeRepositoryImpl() }
}
```

## 기타

- **MainLooper**: 메인(UI) 스레드에서 돌아가는 메시지 루프. UI 갱신은 메인 스레드에서만 가능하고, `Dispatchers.Main`이 이 위에서 동작함.
- **Coil**: Kotlin, 코루틴 기반 이미지 로딩 라이브러리. `AsyncImage(model = url, contentDescription = ...)`로 사용.
- **Preview에서는 네트워크 통신 불가**: Coil로 불러오는 이미지가 안 보임. `placeholder`를 지정하거나, `LocalInspectionMode.current`로 Preview일 때 로컬 리소스를 보여주도록 분기.
- **LazyColumn**: 스크롤 가능한 리스트. **화면에 보이는 아이템만 그려서** 성능이 좋음. `items(list, key = { it.id })`처럼 key를 지정하면 아이템 추가, 삭제 시 상태가 유지되고 불필요한 리컴포지션이 줄어듦.

## Flow.first() vs List.first()

```kotlin
repository.getRecipes()   // Flow<List<Recipe>>
    .first()              // ① Flow의 first → List<Recipe>
    .first()              // ② List의 first → Recipe
```

| **구분** | **누구의 함수** | **하는 일**               | **결과**                  |
| ------ | ---------- | ---------------------- | ----------------------- |
| **①**  | Flow       | Flow가 보내는 첫 번째 값을 받고 끝 | `List<Recipe>` (레시피 목록) |
| **②**  | List       | 목록의 첫 번째 요소            | `Recipe` (첫 번째 레시피)     |

- **`Flow.first()`는 내부에서 collect를 대신 해줌**: 값 하나를 받으면 바로 수집을 멈추고 그 값을 반환. suspend 함수라 `runTest { }`나 코루틴 안에서만 호출 가능.
- **`collect { }`**: Flow가 값을 보낼 때마다 계속 받음. Flow가 끝나지 않으면 계속 기다림.
- **사용 기준**:
  - **테스트**: 지금 값 하나만 확인하면 될 때 → `first()`가 간단함.
  - **ViewModel**: 데이터가 바뀔 때마다 화면도 바뀌어야 할 때 → `collect` (또는 `stateIn`). DB처럼 계속 값이 바뀌는 Flow에 `first()`를 쓰면 첫 값만 받고 이후 변경을 놓침.
- 둘 다 비어 있으면 `NoSuchElementException`이 발생함. 없을 수도 있으면 `firstOrNull()` 사용.
