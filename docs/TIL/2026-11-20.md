## UI State 홀더 패턴 (단일 UiState)

> 화면 상태가 많아지면 StateFlow가 여러 개로 흩어져서 관리가 어려워짐 → 화면 상태를 **하나의 data class로 묶어서 하나의 StateFlow로** 노출하는 패턴.

- **용어 참고**: 공식 문서에서는 이 data class를 **UI State**, 이걸 들고 있으면서 로직을 처리하는 ViewModel(또는 일반 클래스)을 **상태 홀더(State Holder)** 라고 부름.

```kotlin
data class SearchUiState(
    val query: String = "",
    val recipes: List<Recipe> = emptyList(),
    val isLoading: Boolean = false,
)

class SearchViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(SearchUiState())
    val uiState: StateFlow<SearchUiState> = _uiState.asStateFlow()

    fun onQueryChange(query: String) {
        _uiState.update { it.copy(query = query) }
    }
}
```

- **ViewModel은 UI 상태 하나를 가짐**: View는 `uiState` 하나만 구독하면 됨.
- **상태 변경은 `copy()`로**: 기존 객체를 고치지 않고 새 객체를 만들어서 불변성 유지.
- **`update { }`는 Thread-safe**: 읽기 → 수정 → 쓰기를 원자적으로 처리함 (중간에 다른 변경이 끼면 다시 시도). `_uiState.value = _uiState.value.copy(...)`는 그 사이에 다른 코루틴이 바꾼 값을 덮어쓸 수 있음.
- **장점**: 코드가 간결하고, 화면 상태를 한눈에 볼 수 있고, 테스트할 때 `uiState` 하나만 검증하면 됨.
- 반드시 필요한 건 아님

### 단일 data class의 한계 → sealed interface로 분리

- `isLoading = true`이면서 `errorMessage`도 있는 상태처럼 **있을 수 없는 조합**도 만들어질 수 있음.
- **sealed interface로 상태를 배타적으로 분리**: 한 번에 하나의 상태만 가질 수 있음.

```kotlin
sealed interface RecipeUiState {
    data object Loading : RecipeUiState
    data class Error(val message: String) : RecipeUiState
    data class Success(
        val recipes: List<Recipe>,
        val isRefreshing: Boolean = false,
        val userMessage: String? = null,
    ) : RecipeUiState
}
```

- `when`으로 분기하면 컴파일러가 모든 경우를 처리했는지 검사해 줌.
- **Success 안에 `isRefreshing`, `userMessage`**: 새로고침할 때 Loading으로 바꾸면 리스트가 사라지니까, Success를 유지한 채 플래그만 바꿔서 **기존 리스트를 보여주면서 새로고침**. 새로고침 실패 메시지도 리스트 위에 띄울 수 있음.

### data class vs sealed interface 선택 기준

> 상태들이 **동시에 존재할 수 있으면 data class**, **하나만 존재해야 하면 sealed interface**.

| **구분**    | **data class**             | **sealed interface**                |
| --------- | -------------------------- | ----------------------------------- |
| **상태 관계** | 여러 값이 **동시에** 유효함          | 상태끼리 **배타적** (하나만 유효)               |
| **화면 구조** | 화면 틀은 같고 일부 값만 바뀜          | 상태마다 화면 자체가 다름 (로딩 화면 / 에러 화면 / 목록) |
| **예시**    | 입력 폼, 검색어 + 필터 + 결과, 설정 화면 | 첫 로딩 → 성공/실패로 갈리는 목록 화면             |
| **변경 방법** | `copy()`로 일부 필드만 바꿈        | 상태 자체를 다른 타입으로 교체                   |

- **data class가 맞는 경우**
  - **필드끼리 독립적**: 검색어, 선택한 필터, 체크박스 값처럼 서로 상관없이 각자 바뀌는 값.
  - **동시에 보여야 하는 값**: 검색어를 입력하는 동안 기존 결과 목록도 보이고, 그 위에 로딩 표시도 뜨는 화면.
  - **입력 폼**: 이름, 이메일, 비밀번호 같은 값과 각각의 에러 메시지가 동시에 존재함. sealed로 나누면 오히려 표현이 안 됨.
  - **상태가 바뀌어도 계속 남아야 하는 값**: sealed는 상태를 바꿀 때 객체를 통째로 교체해서, 이전 상태가 들고 있던 값이 같이 사라짐. 검색어나 필터를 Success 안에 두면 Loading/Error로 넘어가는 순간 검색창이 비거나 필터가 초기화됨. 이런 값은 data class 필드로 두고 `copy()`로 나머지만 바꿔야 유지됨.
- **sealed interface가 맞는 경우**: 첫 진입 시 Loading → Success / Error처럼 **상태에 따라 화면이 통째로 바뀌고**, 같이 있으면 안 되는 조합이 생길 때.
- **섞어 쓰기도 가능**: 독립적이거나 계속 유지해야 하는 값은 data class 필드로 두고, 배타적인 부분만 sealed 타입 필드로 넣음.

```kotlin
data class SearchUiState(
    val query: String = "",                              // 항상 존재
    val filter: FilterSearchState = FilterSearchState(), // 항상 존재
    val result: SearchResult = SearchResult.Idle,        // 배타적인 부분만 sealed
)

sealed interface SearchResult {
    data object Idle : SearchResult
    data object Loading : SearchResult
    data class Success(val recipes: List<Recipe>) : SearchResult
    data class Error(val message: String) : SearchResult
}
```

## Modifier vs 별도 파라미터

> 컴포넌트 내부의 아이콘 크기 같은 건 Modifier로 넘길 수 없음 → **별도 파라미터**로 받아야 함.

- 넘긴 Modifier는 컴포넌트의 **바깥 틀(루트 레이아웃)** 에만 적용됨. 안쪽 Icon, Text는 각자 자기 Modifier와 style을 쓰니까 바깥 Modifier가 안까지 들어가지 않음.
- 글씨 크기(`TextStyle`)는 Modifier로 아예 못 넘김.

```kotlin
RecipeRating(
    modifier = Modifier.size(8.dp), // Row 전체가 8dp로 제한돼 안쪽이 같이 찌그러질 뿐, 별 아이콘만 8dp로 바꿀 수는 없음
    rating = 4.0,
)
```

| **무엇을 바꾸나**                    | **어떻게 넘기나** | **예시**                           |
| ------------------------------ | ----------- | -------------------------------- |
| 컴포넌트를 **어디에, 얼마나 크게** 놓을지 (바깥) | `modifier`  | `align`, `padding`, `size`       |
| 컴포넌트 **안쪽 모양**                 | 별도 파라미터     | `iconSize`, `textStyle`, `color` |

## 컴포넌트 설계 패턴

### Slot 패턴

- 컴포넌트의 일부 영역을 `@Composable () -> Unit` 파라미터로 비워 두고, **호출하는 쪽이 내용을 채우는** 패턴. 예: `Button { Text("확인") }`
- 컴포넌트는 배치만 책임지고, 안에 뭘 넣을지는 자유로워서 재사용성이 높음.

```kotlin
@Composable
fun RecipeCard(
    title: @Composable () -> Unit,
    modifier: Modifier = Modifier,
    action: @Composable () -> Unit = {},
) {
    Row(modifier = modifier) {
        title()
        action()
    }
}
```

## 상태 호이스팅은 "필요한 곳까지만"

> 호이스팅은 "무조건 맨 위로 올려라"가 아니라 **그 상태를 같이 쓰는 곳의 공통 부모까지만** 올리는 것.

- 예: 필터 바텀시트에서 **고르는 중인 값**과 **확정된 값**은 서로 다른 상태임.
- **draft(초안)**: 사용자가 아직 확정하지 않고 **고르는 중인 임시 값**.

| **구분**      | **고르는 중인 값 (draft)** | **확정된 값**                             |
| ----------- | -------------------- | ------------------------------------- |
| **언제 바뀌나**  | 탭 누를 때마다             | Filter 버튼 누를 때                        |
| **누가 필요하나** | 시트 자신만               | 검색 화면, ViewModel                      |
| **어디 두나**   | 시트 내부 (`remember`)   | ViewModel (`state.filterSearchState`) |

- **draft까지 ViewModel로 올리면**:
  - 탭만 눌러도 검색 결과가 바로 바뀌어서 Filter 버튼이 의미가 없어짐.
  - 바깥을 눌러 취소(dismiss)해도 바뀐 값이 남아서 "원래 값으로 되돌리기" 코드를 따로 짜야 함.
- **draft를 시트 내부에 두면**: 시트가 닫힐 때 `remember`도 사라지니까 취소하면 저절로 원래 값으로 돌아가고, 다시 열면 확정된 값(`initialState`)부터 시작함.

```kotlin
@Composable
fun FilterBottomSheet(
    initialState: FilterSearchState,
    onApply: (FilterSearchState) -> Unit,
    onDismiss: () -> Unit,
) {
    var draft by remember { mutableStateOf(initialState) } // 시트 안에서만 쓰는 임시 값
    // ... 탭 누를 때마다 draft = draft.copy(...)
    Button(onClick = { onApply(draft) }) { Text("Filter") } // 확정할 때만 바깥으로
}
```

- 설정 다이얼로그도 보통 이렇게 만듦: **복사본을 편집하다가 확인을 누를 때만 결과를 넘기는** 패턴.

## distinctUntilChanged

- 이전 값과 같으면 버리고, 다르면 보냄. 비교는 기본적으로 `==`(= `equals()`).
  - **String**: 내용 비교. `"chi" == "chi"`면 같은 값으로 보고 버림.
  - **data class**: Kotlin이 **주 생성자에 있는 프로퍼티**로 `equals`를 자동 생성. `copy()`로 만든 새 객체라도 값이 같으면 같은 걸로 봄. 클래스 본문 `{ }` 안에 선언한 프로퍼티(예: `isEmpty`)는 비교에 안 들어감.
  - **일반 class**: `equals`를 오버라이드하지 않으면 **같은 객체(참조)인지만** 비교.

```kotlin
val a = FilterSearchState(time = "Newest", rate = 4, category = "Dinner")
val b = a.copy()  // 새 객체지만
a == b            // true → distinctUntilChanged가 버림
```

- **StateFlow에는 붙일 필요 없음**: StateFlow는 이미 같은 값을 무시하기 때문에 `StateFlow.distinctUntilChanged()`는 효과가 없어서 컴파일 에러로 막혀 있음. `combine` 결과 같은 일반 Flow에 사용.

# 3. 트러블 슈팅

## 콘텐츠 + 북마크를 하나의 UiState에 섞었더니 코드가 복잡해짐

- **문제**: sealed UiState(Loading / Error / Success)에 북마크 상태까지 같이 넣었더니, 북마크를 처리할 때마다 `when`으로 Success인지 분기해야 해서 코드가 지저분해짐.
- **해결**: 북마크 상태는 별도 StateFlow로 분리.
- **배운 점**: 상태 홀더에 모든 상태를 몰아넣을 필요는 없음. 바뀌는 원인과 시점이 다른 상태는 따로 두는 게 단순한 것 같다.
